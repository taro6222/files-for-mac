# M1 아홉 번째 개발 단위 검증

검증일: 2026-09-09. M1 진행 중.

## 문제와 수정

감시 등록의 비동기 결과를 기다리는 동안 `watcher == nil`이라는 이유로 `자동 갱신 사용 불가`를 표시하고 있었다. 이제 대기 중에는 `자동 갱신 연결 중…`, 등록이 실패해 반환되면 `자동 갱신 사용 불가`로 구분한다. 따라서 이전 실행에서 사용 불가로 표시된 사실만으로 FSEvents 등록이 실패했다고 확정할 수 없다.

또한 NSOpenPanel에서 같은 폴더를 다시 선택해도 `watchedURL == model.location` 조건 때문에 등록을 건너뛰고 있었다. 명시적으로 같은 폴더를 재선택하면 이전 시도를 취소하고 등록을 다시 시작한다. 늦게 반환한 이전 결과는 기존 취소 검사로 폐기한다. 다른 폴더 선택은 정상 탐색 경로에서 한 번만 등록한다.

이동 메뉴에 `자동 갱신 다시 연결`을 추가했다. 홈과 이미 연결된 상태에서는 비활성화하고, 등록 대기 또는 실패 상태에서는 사용자가 명시적으로 재시도할 수 있다. 자동 무한 재시도는 하지 않는다.

## 검증 방식

기존 23개 UI 검사에 조합별 4개를 추가했다.

1. 처음에는 nil을 반환하는 감시 팩토리를 주입해 연결 중과 실패 표시를 구분한다.
2. 같은 폴더 선택 경로를 실행해 팩토리가 두 번째 호출되고 실제 FSEvents 감시기가 활성화되는지 확인한다.
3. 초기 재열거가 끝나고 새 파일이 없는 상태를 확인한 뒤 파일을 생성한다. 수동 새로고침 없이 해당 파일이 목록에 나타나는지 검사한다.
4. 생성한 파일을 삭제하고 목록에서 제거되는지 검사한다.

등록 성공만 확인하는 테스트와 파일 변경 감지를 구분했다. 원래 OS에서 장시간 대기하는 시스템 호출을 강제 종료한 것은 아니다. 취소된 등록 시도는 OS 호출이 반환된 뒤 해제하며, 사용자가 연결 재시도를 반복하면 반환 전까지 복수의 백그라운드 호출이 남을 수 있다.

## 추가 발견: 삭제 이벤트 누락

실제 임시 폴더에서 외부 파일 생성은 반영됐으나 삭제 후 행이 남았다. Foundation 확인 결과 존재하는 `/private/tmp/.../file`은 `standardizedFileURL`로 `/tmp/.../file`이 되었지만, 삭제된 동일 경로는 `/private/tmp/.../file`로 남았다. 이 차이가 감시 대상 경로와의 비교를 실패시켰다.

이벤트 항목 자체의 존재 여부에 의존하지 않고 상위 폴더를 resolve/standardize해 직접 자식인지 판별하도록 수정했다. 삭제 전·후 모두 같은 감시 대상에 매칭되며 중첩 폴더의 자식은 제외하는 코어 회귀 검사를 추가했다. UI 회귀 검사에도 재연결 후 파일 생성과 삭제의 자동 반영을 각각 추가했다.

## 실제 앱에서 확인한 범위

검증 앱을 다시 실행해 이전에 시스템 선택창에서 지정했던 Desktop fixture를 직접 경로 입력으로 열었을 때 두 항목을 읽었다. 이 별도 bundle ID와 현재 환경에서 재실행 후 목록 접근은 확인했다. 감시 등록은 `연결 중`에 머물렀고 메뉴의 재연결을 한 번 실행해도 같은 상태였다. 원래 시스템 호출 대기를 해결했다고 보지 않는다.
