# 365단계 — 큰 7z 목록의 페이지 조회

## 결과

이전 helper는 허용 항목 수 안에서도 전체 목록 JSON이 응답 상한 8MiB를 넘으면 response-limit으로 실패했다. 35,000개 빈 파일의 실제 7z에서 이 실패를 재현했다. 제품의 목록 요청에 offset/pageSize를 추가하고 SDK에서 해당 범위만 수집하도록 변경했다.

각 페이지는 최대 256항목이며 JSON으로 변환한 item 합계 4MiB를 기준으로 일찍 나눈다. 단일 큰 항목은 기존 프레임 상한 내에서 별도 페이지로 허용한다. 전체 응답 하나의 8MiB와 개별 경로 1MiB, 전체 100,000항목 한도는 유지한다. 부모는 전체 경로 UTF-8 합계 256MiB도 제한한다. 부모는 목록 전체를 반환하므로 이 값이 전체 메모리의 하드 상한은 아니다.

각 페이지의 총수·offset·연속 index·세션 UUID·원본 identity와 metadata를 검사한다. 미완료 상태의 빈 페이지와 바뀐 총수/세션/원본은 거부한다. SDK는 페이지 전후 FD 스냅샷을 재검사하고 부모도 페이지마다 원본·취소·기한을 확인한다. 캐시된 전체 목록을 helper에 유지하거나 원본 경로를 다시 열지 않는다. extract는 기존 전역 item index를 사용한다.

## 검증

- Debug 테스트 제품 빌드 성공(18.35초), Release 앱 빌드 성공(32.68초). 새 번들 패키징·서명·manifest 확인; GUI 실행 없음.
- 실제 App Sandbox 번들 Swift 클라이언트 57개 통과(17.264초). 35,000개의 정확한 이름·종류·크기와 원본 불변 확인. 잘못된 페이지의 총수/순서/index/세션/원본, 빈 페이지, Boolean offset과 누락 필드 등 11가지 입력을 거부했다.
- 실제 격리 helper 50개, 비격리 진단 SDK 142개 통과. 전체 목록 JSON이 8MiB를 넘음을 확인하고 모든 페이지 경계·항목·전역 index 추출을 검사했다. 이름에 제어 문자가 포함된 160항목은 JSON 확장으로 첫 페이지 69항목에서 나뉘며 이름 손실 없이 이어진다. 빈 아카이브와 페이지 간 원본 변경·잘못된 요청도 확인했다.
- 제품과 같은 권한의 별도 native probe 15개 통과. 기존 압축 생성·암호·분할·metadata·취소/원본 보호 회귀 포함.

시험 자료는 고정 SDK의 DOC/7zFormat.txt에 따라 빈 파일 헤더만 작성하는 테스트 전용 writer로 생성하고 공식 7zz로 유효성을 확인한다. 제품에는 writer가 포함되지 않는다. 처음 선택한 ZIP 자료는 7z 전용 handler와 맞지 않았고, 60,000자 이름은 SDK metadata에서 거부됐다. SDK가 읽는 10,000자 이름과 명시한 시험 항목 한도로 바로잡은 후 최종 전체 검증이 통과했다. 초기 실패 기록도 보존하며 통과로 바꾸지 않았다.

[소스·번들·수정 전 재현·최종 검사와 로그 해시](listing-pages-365-verification.json)를 보존한다. 로컬 GUI/전체 AppKit/장시간 시험은 재실행하지 않았고 원격도 수동 재시작하지 않았다.

원격 362 소스 789d9b3 실행은 ARM 작업 전체 성공·Intel의 Build app and test targets 실패로 종료됐다. 이번 목록 변경의 수용 결과는 아니다. 364 소스 311a4e2 실행은 조회 시 진행 중이며 같은 실행을 유지했다.

## 남은 항목

35,000항목 검사를 최대 100,000항목·모든 이름 길이/metadata 수용으로 집계하지 않는다. 최신 양 CPU·지원 환경, CPU/프로세스 트리 자원 경계, 나머지 metadata, 전체 원본 UI·실제 입력·VoiceOver, 외부 서비스·장시간 수용과 정식 서명·공증/설치·업데이트는 미완료다. 인증서·notarytool 프로필은 사용자 준비 중이다.
