# M7 Increment 354 — 분할 7z 생성과 재시작 복구 API

상태: 생성·복구 백엔드 구현 및 headless 검증 완료. 생성 화면의 분할 크기 선택과 복구 안내 연결은 미완료다. 전체 분할 capability와 M7 정식 출시는 완료로 표시하지 않는다.

## 구현

SDK의 seek 가능한 출력 동작을 쓰기 전용 파이프의 write/truncate/end 프레임으로 전달한다. 부모는 위치·길이·종료·전체 상한을 검사하고 같은 대상 폴더의 private staging에서 직접 part를 쓴다. 전체 아카이브를 만든 뒤 다시 나누는 복사본은 없다. 일반 단일 파일 생성 FD와 추출 파이프의 기존 계약은 유지한다. append FD나 잘못된 출력 종류를 거부한다.

공개 `createSplit`은 원본 계획 검증, SDK 정상 종료, 실제 7z 시작 헤더 CRC/전체 길이, part별 SHA-256과 파일 identity를 확인한다. 분할 크기는 16바이트부터 원본의 23,040 MiB 선택값까지 받을 수 있고, 실제 출력 총량 8,000,000,000바이트·1,024 part 제한은 별도 유지한다. 평문·암호/헤더 암호화·기존 압축 옵션을 전달한다.

앱의 private `archive-splits` 저널에는 경로·게시 단계·part identity/해시·rename 의도를 저장하고 파일/디렉터리를 fsync한다. 암호나 원본 입력 경로는 저장하지 않는다. 레지스트리는 현재 UID·0700, 저널은 0600/단일 링크를 요구한다. SHA-256 envelope는 손상 검출이며 같은 사용자 권한의 악성 코드에 대한 인증 수단이 아니다. staging lock으로 동시 복구를 거부한다.

각 part는 RENAME_EXCL로 같은 대상 폴더에 게시한다. 단일 base 아카이브와 기존 후속 part도 충돌로 거부한다. 취소·충돌 시 같은 identity·내용·정확한 이름으로 남은 자체 게시 파일만 되돌린다. 외부 수정·대소문자만 바꾼 이름 변경·무관한 staging 파일·모호한 rename 의도는 위치를 반환하고 보존한다. 부분 게시 전체를 하나의 원자적 연산으로 보장하지 않는다.

`recoverSplitCreation`은 재시작 후 확인 가능한 prepared/부분 publishing 상태를 되돌리고, 이미 committed인 기록은 이후 사용자 수정에 손대지 않는다. building·손상/위조 형식·모호한 intent는 자동 삭제하지 않는다. 별도 CLI probe는 실제 프로세스를 지정 지점에서 종료하고 다른 프로세스에서 복구를 검증하며 앱에는 포함하지 않는다.

- 최종 Debug 빌드가 14.54초에 성공했다. 최종 native 엔진의 최적화 Release가 37.77초에 성공했고 ad-hoc preview 번들의 서명/해시 검증이 통과했다.

- 최종 번들의 helper/library와 바이트 해시가 동일한 SDK 산출물의 native 경계 91개가 통과했다. 위치 지정 스트림을 재구성한 결과를 공식 7-Zip으로 복원하고 잘못된 FD 종류를 거부한다.
- 로컬 GUI·전체 AppKit·장시간 시험은 실행하지 않았다. 남아 있던 과거 시험 앱 하나는 실행 기록을 보존하고 종료했다.

## 남은 항목

분할 크기 선택·저장/복원과 생성 화면 연결, private pending 저널 발견·복구 안내 화면을 이어서 구현한다. SDK 생성 중 세밀한 진행량, 실제 대용량/RSS, 원본 FD의 부모 전달·decoder 격리, 전원 장애/외부 파일 시스템 검증, 최신 두 CPU/지원 OS·원본 UI 대조·물리 입력/VoiceOver, Developer ID/공증은 미완료다. 인증서/프로필은 사용자 준비 중이다. 현재 성공을 제품 전체 완성으로 확장하지 않는다.

빌드 환경 기록: 기본 엔진의 컴파일러는 current_path/getcwd/open, 대체 native 엔진의 dSYM 도구는 CFBundle 디렉터리 열기에서 대기하는 것을 실제 스택 표본으로 확인했다. 해당 빌드 PID만 종료하고 로그/표본을 보존했다. 최종 검증 후보는 임시 명령 래퍼에서 native 엔진과 `-debug-info-format none`을 사용하며 저장소 빌드 스크립트는 변경하지 않는다. 최적화나 파일 안전성 검사 기준을 낮추지 않았고 dSYM 성공을 주장하지 않는다.
