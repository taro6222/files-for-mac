# 367단계 — 큰 비동기 UI 검증 구간 분리

## 변경

364 소스 ARM의 실제 컴파일러 관찰은 LLVM CoroSplit/LazyCallGraph/CoroCleanup에서 활성 계산을 보였고 빌드는 약 639초에 완료됐다. 같은 환경에서 Intel의 이전 앱 빌드는 20분 제한을 넘겼다. 최신 조회에서 364 소스의 Intel 빌드도 정상 완료됐으므로 항상 실패한다고 설명하지 않는다. 관찰을 특정 소스 함수의 원인 증명으로 확대하지 않는다.

BrowserWindow.runUIVerification의 약 200개 await를 가진 큰 본문에서 압축 22개·7z 26개·원본 화면 대조 21개의 await가 있는 구간을 세 개의 MainActor 비동기 함수로 분리했다. 각 함수는 inline하지 않도록 하며 기존 위치에서 순서대로 기다린다. SDK 검사·암호·분할·경계·원본 화면 검사와 실패 분기는 모두 유지한다.

검사 본문에 함수 경계와 들여쓰기만 추가했다. 변경 후 이 경계와 들여쓰기를 되돌리면 변경 전 BrowserWindow.swift 전체와 바이트 단위로 같음을 확인했다. 기존 체크포인트·결과 observer·metrics·diagnostics를 그대로 사용한다. 부모 구간에서 만든 임시 설정의 정리와 최종 보고/종료·오류 처리도 유지한다. 분리 구간 밖에서 해당 구간의 지역 변수를 사용하는 곳이 없음을 확인했고 컴파일로 캡처·actor 격리·가시성을 검사한다.

## 검증과 현재 상태

Debug 앱·테스트 제품 빌드 34.13초와 Release 앱 빌드 16.87초가 통과했다. 첫 Release 시도는 기본 홈 clang 캐시 쓰기를 sandbox가 거부했으며, 작업 폴더의 CLANG_MODULE_CACHE_PATH로 바꾼 실행이 통과했다. 실패 로그도 보존한다. 로컬 GUI·전체 AppKit·장시간 시험은 실행하지 않았다. 검증 본문 불변과 빌드는 실제 AppKit 실행 수용이나 원격 컴파일 시간 개선의 대체 증거가 아니다.

이번 변경은 compiler의 coroutine 변환 작업을 작은 함수로 나누기 위한 수정이다. 동일 원격 도구 체인에서 실제 개선 여부와 전체 검사 결과를 확인해야 하며 Intel 시간 초과를 해결했다고 아직 표시하지 않는다. 기존 진행 중 실행을 관찰 시간 초과 때문에 재시작하지 않는다. 이번 코드는 기본 push 검사와 전체 AppKit을 중복 실행하지 않도록 [skip ci]로 푸시하고 같은 소스의 전체 AppKit workflow_dispatch 한 번을 요청한다. 코드 변경으로 필요한 수용이며 기존 시간 초과 실행의 재시도가 아니다. 대기 중인 이전 제품 소스가 남아 있으면 새 전체 검증과 중복되지 않도록 그 대기 실행만 취소하며, 이미 진행 중인 기존 실행은 유지한다.
