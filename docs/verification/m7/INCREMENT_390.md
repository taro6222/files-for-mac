# 390 — 교환 미지원 볼륨의 다단계 저장/복원과 재개

현재 상태: **서비스·복구 UI 연결, 일부 파일 시스템 수용·추가 검증 중**. F23/M7 전체 완료가 아니다.

## 저장 경로

커널 교환이 가능한 경우 기존 RENAME_SWAP 경로를 유지한다. ENOTSUP/EINVAL/ENOSYS로 거부되면 이동 의도를 저널에 동기화한 뒤 현재 파일→중간 보존 위치, 새 버전→원본 경로, 중간 보존 파일→기존 candidate 위치 순서로 이동한다. 게시·Undo·Redo가 같은 검증 경로를 사용한다. 각 단계의 파일 내용/identity/외부 metadata와 디렉터리 바인딩을 확인하고 디렉터리를 동기화한다.

이 경로는 원자적 교환이 아니며 원본 경로가 잠시 비어 있을 수 있다. 기존 CopyEngine의 no-replace 게시 경로를 재사용한다. 독점 이름 변경도 미지원이면 [Foundation 이동 계약](https://developer.apple.com/documentation/foundation/filemanager/moveitem%28at%3Ato%3A%29)을 사용한다. 존재하는 대상을 덮지 않는 계약과 전후 실제 검증을 사용하는 것이며 모든 외부 동시 생성·상위 경로 변경에서 커널 원자성을 제공한다고 주장하지 않는다.

중단 시 두 버전과 중간 파일을 보존한다. 확인은 배치만 검증하고 중간 상태를 반환하며, 사용자가 복구 화면에서 계속 진행을 확인해야 이동을 재개한다. 마지막 단계까지 끝났으면 실제 두 파일을 확인해 완료 상태를 기록한다. 알 수 없는 배치·외부 파일·metadata 변경은 그대로 두고 오류를 반환한다. 재개 확인 창에는 대상 경로와 보존 정책을 표시한다. 중간 파일도 보존 위치 보기와 상세 영역에 포함하고 확인 전 재개를 비활성화한다.

## exFAT의 실제 관찰과 SDK 수정

전용 raw 디스크 이미지에서 RENAME_SWAP과 RENAME_EXCL이 모두 errno 45로 거부되는 것을 확인했다. Foundation 이동의 세 단계는 바이트와 inode를 유지했고 기존 대상이 있는 경우 두 파일을 보존했다. 모든 시험용 이미지를 정상 detach했다. 실제 사용자 디스크는 포맷하거나 변경하지 않았다.

실제 암호 아카이브 시험에서 빈 exFAT 출력에 처음 데이터를 쓰면 inode가 18446744073709551599에서 19로 바뀌고, 같은 열린 FD와 경로는 둘 다 새 ID 19를 반환하는 것을 재현했다. SDK의 쓰기 전후 inode 동일성 검사 때문에 정상 출력을 source-changed로 거부하고 있었다.

이 경우만 처리하도록 SDK를 수정했다. 같은 전달 FD·같은 device·일반 파일/권한/소유자/그룹/링크 수·쓰기 접근과 입력 파일 비별칭 검사는 유지하거나 강화한다. 빈 출력의 ID 변경은 fstatfs가 exfat인 경우만 허용한다. 부모는 SDK 종료 후 현재 FD와 이름이 가리키는 파일의 identity를 비교하고 별도 read-only worker로 내용/속성을 검증한 뒤 게시한다. 입력 파일 identity 검사는 완화하지 않았다. SDK 권한이나 wire schema는 변경하지 않았다.

## 날짜 보존의 남은 한계

이 Mac의 exFAT에서 fsetattrlist로 생성 시각을 쓰면 source의 440000000ns가 target에서 0ns가 되는 것을 별도 C probe로 확인했다. 1ms를 더해 전달해도 0ns였다. 이는 시험한 FD API/OS의 결과이며 모든 macOS API·버전의 동작이라고 일반화하지 않는다.

생성 시각이 정수 초인 실제 암호 ZIP/7z에서 공개 API의 자동 대체 저장·추출·Undo·Redo와 원본 백업 바이트 보존을 통과했다. 소수 초가 있는 원본은 손실을 허용하지 않고 게시 전 거부해 원본 바이트와 생성 시각을 그대로 보존했다. 이 조건을 숨기거나 exFAT 전체 지원으로 집계하지 않는다. 다른 OS가 정확한 소수 초 왕복을 지원하면 시험은 성공한 저장에서도 원래 시각의 정확한 보존을 요구한다.

## 검증

- 강제 다단계 경로에서 두 버전/Undo/Redo, 저장·Undo·Redo 각각 이동 전/1·2·3단계의 12개 중단 지점 재개, 세 위치의 외부 충돌 보존을 통과했다. 오류 주입 후 새 transaction으로 확인하며 실제 SIGKILL·전원 중단 시험으로 설명하지 않는다.
- 강제 경로의 실제 암호 ZIP/7z 후보·내용 복원·Undo/Redo와 실제 exFAT의 두 mounted 시험이 통과했다. mounted 시험은 정수 초 생성 시각의 성공과 소수 초 손실 거부를 구분한다.
- 최종 Swift SDK 클라이언트 85개, 격리 helper 113개, 진단 205개, native 85개, 권한 15개와 Debug/Release 빌드가 통과했다. 최종 대상 경로 안내 문구 변경은 별도 Debug/Release 빌드로 확인했으며 SDK 검증의 Core/helper 코드는 동일하다.
- 볼륨 matrix에 archiveEditMounted 조건과 전용 exFAT 환경을 연결했다. SDK fixture가 있으면 암호 포맷 시험도 실행한다. 신규 재개 UI는 기존 375개 정의의 비활성 조건을 보강했고 실제 긍정 동선/물리 입력/VoiceOver 수용은 대기 중이다.

[소스·원본 probe·최종 결과 해시](archive-rename-390.json). 로컬 GUI·전체 AppKit·장시간 시험 앱은 실행하지 않았다. 388 DMG에는 이번 변경이 없다.

## 원격 상태와 남은 요구

c4c4f6e의 45888418153은 양 CPU 전체 작업 성공으로 종료했다. b6a999e의 45890631779는 ARM 성공·Intel 프리뷰 빌드/설치 단계 15분 제한으로 실패했다. 0079406의 45892370861은 Intel의 DifferentGroupChildCollected 빌드 관찰 시험 실패가 확인됐다. 로그는 build/edit-390-ui387-failed.log와 build/edit-390-ci388-failed.log에 보존했다. 결과를 재실행으로 대체하지 않았고 인프라 실패의 원인과 수정은 별도 확인이 필요하다.
