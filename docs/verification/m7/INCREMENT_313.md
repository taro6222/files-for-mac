# M7 Increment 313 — 최근 기록 행 재사용과 관찰 객체 누적 대조

상태: 메모리 누적의 한 경로를 줄였으며 로컬 UI 회귀를 통과했다. 장시간 메모리 게이트와 M7 출시는 미완료다.

실행 중인 `5284cb3` 기준 앱의 힙에서 브라우저와 주 표는 각각 한 개였지만 AppKit 관찰 컨텍스트는 41,896개였다. 참조 그래프의 큰 스택 경로를 역추적해 주 창의 `homeRecentView`임을 확인했다. 이 소스와 `56d0ffc`의 최근 기록 갱신 함수 본문은 동일하다. [보유 경로 발췌](recent-row-memory-ownership.txt).

최근 위치·최근 파일은 행을 매번 제거·생성하지 않고 기록의 최대 사용 행 수까지 슬롯을 재사용한다. 비활성 슬롯은 숨기고 URL·메뉴를 비우며 클릭을 비활성화한다. 현재 URL에 맞는 메뉴를 갱신하고, 재정렬 전에 초점의 액션·레이블·URL을 값으로 저장해 같은 논리 항목에 초점을 복원한다. 위치·파일·태그·홈 전체 갱신의 초점 복원도 이 값 스냅샷을 사용한다. 제품에는 private AppKit 필드 변경이나 SDK 메타데이터 변경을 사용하지 않는다.

같은 `56d0ffc`에서 보관한 기준 소스와 행 재사용 후보를 같은 도구·SDK·최적화 QA 설정으로 각각 180초 실행했다. 두 실행은 같은 호스트에서 겹쳐 실행됐고 기존 기준 장시간 시험도 유지했다. 각각 62·61사이클 후 정상 종료했다. `heap`은 두 실행 모두 5→40사이클의 동일 지점에서 수집했다.

| 관찰 컨텍스트 | 5사이클 | 40사이클 | 증가 | 사이클당 증가 |
|---|---:|---:|---:|---:|
| 기준 | 1,087 | 1,577 | 490 | 14 |
| 행 재사용 | 1,061 | 1,236 | 175 | 5 |

증가량은 이 구간에서 64.3% 감소했지만 계속 증가한다. 두 표본의 브라우저·주 표 수는 각각 1개로 유지됐다. 다른 익명 뷰의 보유 경로는 native `NSTabBar`의 `_tabContainer`에서 확인했다. 이 관찰만으로 잔여 증가 전체의 원인을 확정하지 않는다. [실행·소스·바이너리·힙 해시와 실제 표본](recent-row-memory-comparison.json). 짧은 객체 수 대조를 8시간 메모리 안정성으로 대체하지 않는다.

최근 위치를 200회 재정렬하는 검사에서 행 객체의 동일성, 메뉴 URL과 논리 URL 기준 초점을 확인했다. 전체 회귀에서 재사용된 숨김 행을 마지막 버튼으로 선택하던 시험을 발견해, 표시된 파일 버튼을 URL로 찾아 재열기·순서 변경을 검사하도록 수정했다. 제품 경로는 이 시험 수정 전후에 동일하며 대조 소스와 최종 소스의 차이를 증거에 기록한다.

별도 `56d0ffc` ARM CI는 저장 태그 기대값과 빈 열거 결과의 불일치를 검출했다. 이 실패는 메모리 수정으로 해결했다고 표시하지 않는다. 원격 태그 읽기 경로의 보강·실환경 재검증, 잔여 관찰 객체 증가·최신 소스 8시간, Intel 성능, 실제 접근성·서명·공증 수용은 남아 있다.

Debug·일반 Release·두 최적화 QA 빌드가 성공했다. 최종 고정 Debug SHA-256은 `6d84adaddc0cc245a78cbc1c3491a7e4a075a21655900ebff5465d7d633405d3`이다. 한국어/영어 × 밝게/어둡게 네 조합 각각 파일 작업 UI 78개·전체 AppKit 283개가 통과했다. Core 제품 코드는 변경하지 않아 별도 Core 전체 시험은 이 단계에서 반복하지 않았다. [최종 소스·바이너리·원본 보고서 해시와 미해결 ARM 태그 진단](recent-row-reuse-verification.json).
