# M7 Increment 98 — 성능 측정 소스 고정

성능 검증 스크립트는 시작 시점의 Git 커밋을 임시 디렉터리에 추출하고 그 소스로 최적화 QA 바이너리를 빌드한다. 보고서의 소스 SHA는 추출에 사용한 값이다. 실행 중 작업 트리가 바뀌거나 후속 커밋이 들어와도 이미 시작한 시험의 바이너리와 보고서가 가리키는 소스가 일치한다.

macOS에서 `fdcdb88` 스냅샷의 파일 541개를 Git 아카이브와 바이트 단위로 대조했다. Apple Silicon macOS 27.2 (26B123), APFS, 공유 OS 캐시에서 최적화 바이너리를 실행했다. [측정 표본](performance-fdcdb88.json)

| 지표 | 결과 |
|---|---:|
| 10,000항목 첫 표시 p95, 20회 | 58.5 ms |
| 10,000항목 전체 표시 p95, 20회 | 1.261초 |
| 100,000항목 첫 표시 최댓값, 3회 | 59.0 ms |
| 100,000항목 전체 표시 범위, 3회 | 11.47–13.16초 |
| 5분 유휴 RSS, 1회 | 95.4 MB |
| 5분 유휴 후 10,000항목 전체 표시, 1회 | 6.927초 |

일반 20회에서는 10,000항목 전체 표시 p95가 2초 목표를 충족했다. 5분 유휴 후의 단일 표본은 2초를 초과했다. 유휴 후 반복 탐색과 콜드 시작, 화면 합성 프레임은 별도 확인이 필요하다.

`bash scripts/verify-release-performance.sh m7-idle idle-comparison`으로 같은 최적화 바이너리와 APFS의 10,000항목 폴더를 사용해 즉시 탐색과 5분 유휴 후 탐색을 세 쌍 실행한다. 각 표본은 새 앱 프로세스를 사용한다. 기본 모드의 10,000항목 20회, 100,000항목 3회, 5분 유휴 1회는 유지한다. 두 모드 모두 계측 바이너리 대역으로 측정 횟수, 폴더 항목 수, 대기 설정과 보고서 형식을 검증했다.

실제 `23e36e9` 빌드의 [세 쌍 측정](performance-idle-23e36e9.json)에서 즉시 전체 표시는 1.127–1.344초, 5분 유휴 뒤 전체 표시는 4.935–6.933초였다. 첫 표시는 즉시 60–76 ms, 유휴 뒤 218–299 ms였다. 실행 중 스크립트를 편집해 보고서 저장 이후 셸 종료 오류가 발생했다. 저장된 보고서의 여섯 표본을 각 앱의 개별 출력과 대조했다.
