# 384 — 긴 복구 경로의 잘림 수정

381/382의 실제 밝은 화면 캡처에서 긴 보존/기록 경로가 오른쪽에서 잘렸다. 창을 만들지 않는 AppKit 텍스트/스크롤 뷰 검사로 재현했다. 844pt 문서를 초기 크기 0인 스크롤 뷰에 넣고 나중에 크기를 적용하면 자동 폭 조정으로 문서가 1,686pt까지 늘어났고 실제 뷰포트는 842pt였다. 텍스트는 넓은 문서 안에서 배치돼 화면 밖으로 넘어갔다.

복구 상세 스크롤 뷰에 실제 초기 크기 844×130을 지정했다. 같은 검사에서 문서/뷰포트가 842pt로 일치하고 긴 경로가 줄바꿈된다. 최소 창 폭에 해당하는 경우도 문서/뷰포트 762pt로 일치했다. 더 긴 내용은 165pt 높이로 확장돼 전체 내용을 수직 스크롤할 수 있다.

| 창 없는 실제 측정 | 문서 폭 | 표시 폭 | 내용 폭 | 문서/내용 높이 |
|---|---:|---:|---:|---:|
| 이전 구성 | 1686 | 842 | 1360.07 | 128 / 30 |
| 수정 초기 폭 | 842 | 842 | 840.81 | 128 / 45 |
| 수정 최소 폭 | 762 | 762 | 736.96 | 128 / 45 |
| 수정 긴 내용 | 762 | 762 | 736.96 | 165 / 165 |

`Tools/ArchiveRecoveryLayoutProbe/main.swift`는 NSWindow/NSApplication 실행 없이 이 구성을 측정하고 이전 넘침 재현과 수정 구성의 폭/높이 범위를 확인한다. 읽기 전용 텍스트 설정을 실제 화면과 맞췄다. 이는 전체 창의 실제 렌더링 수용을 대신하지 않는다. 예시 실행은 명시적 macOS SDK·14.0 target·`-parse-as-library`로 컴파일한 뒤 출력 JSON을 확인한다. 도구는 앱 번들/제품 target에 포함하지 않는다.

기존 `archiveHistoryDetailsVisible` 검사에 실제 문서/컨테이너/내용 폭과 문서 높이 조건을 더했다. 전체 UI 조건 수 369개는 유지하며, 글자가 조금 보이는 것만으로 성공하지 않는다. Core·SDK·복구 데이터/Undo 동작은 바꾸지 않았다. 최종 Debug 7.63초·Release 15.80초 빌드와 공백 검사를 통과했다. 로컬 GUI·장시간 시험 앱은 실행하지 않았다.

## 원격 상태와 산출물 구분

기존 [45882828053](https://github.com/taro6222/files-for-mac/actions/runs/45882828053)는 수정 전 7e31fc6의 실행이며 그대로 유지한다. ARM의 ko-light/ko-dark는 각각 369개를 통과했다. en-dark는 로그에 세부 코드가 없는 압축 오류로 조기 종료했고 en-light는 암호 prompt 누락 뒤 후속 검사 실패/시간 초과였다. 고정 Git fixture의 내용/commit은 이 실행에서도 통과했다. Intel은 관찰 시 SDK용 앱 준비 빌드 중이었다. 이 결과를 새 레이아웃의 수용으로 집계하지 않는다.

새 GUI 수용은 아직 미완료다. 383의 DMG는 7e31fc6 앱 코드를 담은 이전 프리뷰이며 이 수정은 포함하지 않는다. 기존 이미지/체크섬은 보존하고, 통합 검증 후 새 산출물을 만든다. 정식 출시/서명/공증과 F23/M7 전체 수용은 미완료다. [소스·실측·빌드 기록](archive-layout-384.json).
