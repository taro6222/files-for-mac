# M7 Increment 173 — 상세 목록의 빈 상태 전환과 장시간 메모리

Apple Silicon macOS 27.2 (26B123)에서 이전 전체 부하 시험의 7시간대 힙을 분석했다. `leaks`는 미참조 할당 0건을 보고했다. 참조 트리에는 AppKit의 `previousKeyViews` 아래 약 30.5 MB가 남았고 그중 약 27.2 MB는 주 상세 목록의 관찰 의존성 경로였다. `NSKeyValueDependencyContext`는 492,639개, `NSKVONotifying_NSScroller`는 13개였다. 0건의 미참조 할당과 별개로 장시간 객체 보유가 확인됐다.

최소 AppKit 대조에서 129개 행을 비웠다가 다시 표시했다. 전체 다시 읽기를 쓰면 4→120사이클에서 컨텍스트가 555→4,267개로 증가했다. 스크롤 뷰 분리 여부나 첫 응답자 지정과 관계없이 재현됐다. 행 제거·삽입을 사용하면 같은 구간에서 458개로 유지됐다. 제품의 상세 목록도 실제 행이 생기거나 모두 사라지는 경우 행 갱신으로 처리한다. 내용이 있는 상태에서 정렬·그룹·표시 변경이 발생하면 전체 다시 읽기를 사용한다.

같은 환경에 최적화 빌드를 두고 AppKit 컨텍스트의 사이클당 증가를 비교했다. 두 빌드의 표본 시작 수가 달라 해당 구간의 증가량을 기록했다.

| 부하 | 기존 증가 | 수정 증가 |
|---|---:|---:|
| 탐색, 4→20사이클 | 506 | 352 |
| 탐색·탭, 4→20사이클 | 768 | 592 |
| 독립 창, 5→21사이클 | 578 | 512 |

세 부하 모두 증가가 줄었고 계속 누적됐다. 마일스톤의 8시간 메모리 안정성 검증은 진행 중이다. 행 변경 전에 빌드한 소스 `0a7b50b50adfa810c8d93802e4b532f1ff2080e2`에서 같은 전체 부하 8시간 시험도 시작했다. 바이너리 SHA-256은 `9cfd0c5fee1b1f58b21c29c770f638cce5b1ae68856a462e6ca01de6e76d25d9`이다.

변경 후 로컬 최적화·디버그 빌드가 성공했다. AppKit 자동 회귀는 한국어·영어와 밝은·어두운 테마의 네 조합마다 269개 통과했다. 별도 데스크톱 연결은 초기화 시간 초과로 종료되어 VoiceOver 출력은 검증하지 못했다.

행 갱신 전 빌드의 전체 부하는 [8시간 기준 기록](INCREMENT_248.md)에 저장했다.
