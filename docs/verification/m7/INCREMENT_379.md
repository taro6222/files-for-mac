# 379 — 빈 ZIP과 추가 파일의 명시적 암호 정책

파일 추가 창에 ‘추가 파일 암호화’ 선택을 연결했다. 기존 암호화 파일이 남아 있으면 선택을 켜고 해제를 막는다. 파일이 없는 ZIP(폴더만 남은 경우 포함)은 기본적으로 암호화를 선택하며 사용자가 명시적으로 해제할 수 있다. 기존 암호를 자동으로 저장하거나 추정하지 않고 선택에 따라 저장 시 암호를 입력받는다. 원래 평문 파일이 있는 압축에서는 추가 파일의 암호화를 직접 선택할 수 있으며 기존 항목의 보호 상태는 유지한다.

마지막 암호화 ZIP 파일을 지우기 전 기존 원본 보존과 이후 파일 추가 시 암호화를 다시 선택해야 한다는 안내를 표시한다. 암호화 7z 헤더를 읽었던 상태도 별도의 bool로 유지해 항목이 비어 있어도 암호화 선택 해제를 막는다. 암호 문자열은 설정/저널에 저장하지 않는다. 기존 source version·전체 검증·백업/Undo 경로는 유지한다.

## 검증

- 최종 Debug 7.68초·Release 16.26초 빌드와 번들 서명/SDK 검증 통과. 로컬 GUI는 실행하지 않았다.
- 실제 번들 Swift 회귀 74개 통과. 추가 1개는 암호 ZIP의 마지막 파일 삭제, 빈 ZIP 확인, 암호 누락 재추가 거부/원본 보존, Unicode 새 암호로 재추가·복호화, 명시적 평문 재추가, 각 Undo와 최초 원본의 바이트 일치를 확인한다.
- 최초 시험 실패는 일반 7z reader로 ZIP 목록을 읽은 시험 코드였다. ZIP 편집 출력은 제품과 같은 ZIP reader로 확인하도록 수정했다. 제품의 검증 조건은 완화하지 않았다.
- Python/셸 구문과 diff 공백을 확인했다. SDK·Core 엔진 소스는 변경하지 않아 기존 native 205/113/85 조건을 반복하지 않았다.
- UI 정의는 기존 361개를 유지하고 잠긴 암호화 선택·마지막 암호화 파일 안내·빈 ZIP 기본값·암호 입력 취소 보존·암호화 추가·명시적 해제/평문 추가·빈 암호 7z 헤더 보호 8개를 더해 369개다. `archive-add-encryption` 캡처를 추가했다. 정의와 컴파일을 실제 UI 수용으로 집계하지 않는다.

## 기존 원격 결과

이전 [45873718296](https://github.com/taro6222/files-for-mac/actions/runs/45873718296)는 양 CPU 모두 **실패로 종료**했다. Intel의 네 조합에서도 새 편집 관련 28개와 탭 경계 18개가 각각 통과했고 전체 UI는 동일한 다중 창/행 수 두 조건에서 실패했다. ARM의 en-dark 일괄 배치 실패는 Intel에서는 재현되지 않았다. 양 CPU의 실제 보고서를 보존했으며 결과가 다른 조건의 원인은 확정하지 않는다.

378의 [45877111686](https://github.com/taro6222/files-for-mac/actions/runs/45877111686)는 그대로 유지하며 관찰 시 두 CPU 빌드 중이었다. 이번 추가 UI의 원격 수용은 아직 시작/완료로 집계하지 않는다. 로컬 GUI/장시간 앱은 재시작하지 않았다.
